# Shuffla YouTube 자동화 서비스 전략 기획서

> **문서 버전:** 1.0  
> **작성일:** 2026-06-26  
> **기준 코드베이스:** `snsagent` (Shuffla) `main` 브랜치  
> **작성자:** Shuffla Product Team  

---

## 1. Executive Summary

Shuffla YouTube 자동화는 **주제 하나만 입력하면 30일분의 쇼츠 영상을 자동으로 기획·제작·다운로드할 수 있는 턴키(Turn-key) 서비스**다. 사용자는 채널 주제를 입력하고, 시스템은 LLM으로 30개의 클릭 유도 제목을 생성한 뒤, 매일 하나씩 오픈되는 캘린더에서 "제작안 생성 → MP4 렌더링 → 다운로드" 과정을 거친다.

각 영상은 무료 스톡 영상(Pexels/Pixabay)을 씬별로 잘라 붙이고, OpenAI TTS(`gpt-4o-mini-tts`) 나레이션과 ASS 자막을 합성하는 방식으로 제작된다. 영상 생성 AI를 사용하지 않으므로 **원가가 낮고 렌더링 속도가 빠르다**는 것이 핵심 차별점이다.

본 문서는 현재 구현 상태를 분석하고, 프라이싱 모델, 확장 가능성, 기술적·비즈니스적 문제점과 해결 방안을 종합적으로 제시한다.

## 2. 서비스 개요

### 2.1 핵심 가치 제안

| 항목 | 설명 |
|------|------|
| **문제** | 유튜브 쇼츠 채널 운영은 기획·대본·편집·자막·업로드 등 매일 반복되는 노동 집약적 작업 |
| **해결** | 주제 입력 한 번으로 30일분 영상 기획·제작 자동화. 사용자는 다운로드 후 업로드만 수행 |
| **차별점** | 영상 생성 AI 미사용 → 원가 절감(영상당 ~$0.02 vs AI 영상 생성 $0.30~$2.00) + 빠른 렌더링(60초 영상 ~30초) |
| **타겟** | 부업 유튜버, N잡러, 소상공인, 콘텐츠 에이전시 |

### 2.2 현재 구현 범위

```
주제 입력 → 30일 플래너 생성 (LLM)
         → 매일 1개씩 캘린더 오픈 (24시간 잠금)
         → Day 제작안 생성 (LLM: 대본, 씬 구성, 검색 키워드)
         → 스톡 영상 검색 (Pexels → Pixabay fallback)
         → TTS 음성 생성 (OpenAI gpt-4o-mini-tts, 프로젝트별 랜덤 음성 고정)
         → ffmpeg 합성 (영상 컷 + TTS + ASS 자막 + 썸네일)
         → Vercel Blob 저장 → MP4/썸네일/TTS 다운로드
```

### 2.3 기술 스택

| 계층 | 기술 |
|------|------|
| 프론트엔드 | Next.js 15 (App Router), React 19, TypeScript |
| 백엔드 API | Next.js Route Handlers (Node.js runtime, maxDuration 600s) |
| AI / LLM | OpenAI GPT-5.5 (텍스트 기획), gpt-4o-mini-tts (음성) |
| 영상 처리 | ffmpeg (자막 합성, 컷 편집, 오디오 정합), @ffmpeg-installer/ffmpeg |
| 스톡 영상 | Pexels Video API, Pixabay Video API |
| 데이터베이스 | PostgreSQL (Prisma ORM), Mock JSON fallback |
| 스토리지 | Vercel Blob Storage |
| 결제 | Toss Payments (국내), PayPal Subscription (해외), Polar (신규) |
| 인프라 | Vercel (Serverless), Inngest (백그라운드 잡) |

## 3. 현재 구현 상세

### 3.1 데이터 모델

```
YouTubeAutomationProject (프로젝트 = 30일 캘린더)
├── topic          채널 주제
├── status         planned → in_progress → completed
├── currentOpenDay 현재 오픈된 날짜 (1~30)
├── ttsVoice       프로젝트 생성 시 랜덤 고정된 TTS 음성 (alloy/echo/fable/onyx/nova/shimmer)
└── days[]         YouTubeAutomationDay (30개)

YouTubeAutomationDay (하루 = 1개 영상)
├── dayNumber      1~30
├── scheduledDate  예정 날짜
├── title          쇼츠 제목
├── status         locked → open → planning → ready → rendering → completed → uploaded
├── script         전체 대본
├── scenesJson     씬별 나레이션, 검색 키워드, 목표 길이
├── sourceClipsJson Pexels/Pixabay에서 검색된 스톡 영상 후보
├── ttsProvider    사용된 TTS 모델
├── ttsAudioUrl    합성된 음성 파일 URL
├── subtitleJson   실제 TTS 길이 기반 자막 타이밍
├── mp4Url         최종 영상 URL
└── thumbnailUrl   썸네일 URL
```

### 3.2 영상 제작 파이프라인

```
[1] TTS 생성 (씬별)
    ├── createSceneSpeechAudio(narration, voice)
    ├── OpenAI audio.speech.create(model, voice, input)
    └── probeAudioDuration() → 실제 오디오 길이 측정

[2] 스톡 영상 다운로드 + 컷
    ├── downloadVideo(pexels/pixabay URL)
    └── normalizeClip() → 1080x1920, 30fps, TTS 길이에 맞춰 컷

[3] 오디오 합성
    └── concatenateAudio() → 씬별 TTS를 하나의 speech.mp3로

[4] 자막 생성
    └── buildAssSubtitlesWithDurations() → 실제 TTS 길이 기반 ASS 자막

[5] 최종 합성
    └── ffmpeg: concat 영상 + speech 오디오 + ASS 자막 + Pretendard 폰트

[6] 썸네일 추출 + 저장
    ├── ffmpeg -ss 00:00:01 -frames:v 1
    └── Vercel Blob 업로드 (mp4, thumbnail, tts mp3)
```

**핵심 설계 원리:** TTS가 영상 길이를 결정한다. LLM이 계획한 `durationSeconds`는 참고용이며, 실제 TTS 오디오 길이를 측정(probe)한 후 영상 컷과 자막 타이밍을 그에 맞춘다. 이렇게 하면 음성과 영상이 완벽히 싱크된다.

### 3.3 접근 제어 및 게이밍 방지

| 메커니즘 | 구현 |
|---------|------|
| **플랜 게이팅** | Creator(월 25,000원) 이상만 사용 가능. FREE 플랜은 업그레이드 프롬프트 |
| **1일 1영상 잠금** | `currentOpenDay` 추적. 하루 영상을 업로드 처리해야 다음 날이 오픈됨 |
| **24시간 쿨다운** | 완료된 영상은 24시간 후에만 다시 렌더링 가능 (localStorage 타임스탬프) |
| **렌더링 중 방지** | `status === 'rendering'`일 때 409 Conflict 반환 |

## 5. 확장 가능성

### 5.1 단기 확장 (3~6개월)

#### ① YouTube 직접 업로드 연동
- **현재:** MP4 다운로드 후 수동 업로드
- **확장:** YouTube Data API v3 연동으로 자동 업로드
- **가치:** 사용자 조작 최소화, "진정한 자동화" 완성
- **구현:** OAuth 2.0 (YouTube scope), 예약 업로드, 제목/설명/태그 자동 입력
- **난이도:** 중 (API 연동은 단순하나 OAuth 플로우와 토큰 관리 필요)

> **⚠️ YouTube Data API 할당량(Quota) 제약 — 핵심 설계 고려사항**
>
> YouTube Data API v3는 일일 할당량(Quota)이 존재하며, 이것이 자동 업로드 기능의 확장성을 좌우한다.
>
> | 작업 | 할당량 비용 | 비고 |
> |------|-----------|------|
> | 영상 업로드 (`videos.insert`) | **1,600 units** | 1회 업로드당. 기본 할당량 10,000 units/일 기준 **하루 6개 업로드 가능** |
> | 검색 (`search.list`) | 100 units | 트렌드 분석, 경쟁 영상 분석 시 사용 |
> | 영상 정보 조회 (`videos.list`) | 1 unit | 조회수/통계 확인 시 사용 |
> | 채널 정보 조회 (`channels.list`) | 1 unit | |
> | 댓글/재생목록 등 쓰기 작업 | 50 units | update, insert, delete |
>
> **기본 할당량:** 10,000 units/일 (프로젝트당)
> - 영상 업로드만 사용 시: **하루 6개** (10,000 ÷ 1,600)
> - 1사용자 30일 프로젝트 = 30영상 → **한 번에 6개씩 5일에 걸쳐 업로드** 필요
>
> **확장 시나리오별 할당량 분석:**
>
> | 동시 사용자 수 | 일일 필요 units | 기본 할당량 내? | 대응 방안 |
> |--------------|--------------|:---:|---------|
> | 10명 (30영상씩) | 48,000 | ❌ | 할당량 연장 신청 필요 |
> | 50명 | 240,000 | ❌ | 멀티 프로젝트(GCP) 분산 필요 |
> | 500명 | 2,400,000 | ❌ | 사용자별 개별 OAuth + 사용자 할당량 활용 |
>
> **핵심 전략: 사용자 OAuth 기반 업로드 (서버 할당량 소진 방지)**
>
> 가장 중요한 설계 결정: **사용자 본인의 YouTube 계정으로 OAuth 인증하여 업로드**하면, 할당량이 **사용자의 Google Cloud 프로젝트가 아닌 Google의 글로벌 풀에서 소진**된다. 즉, Shuffla 서버의 API 키 할당량을 소진하지 않는다.
>
> | 방식 | 할당량 소진 주체 | 확장성 | 구현 복잡도 |
> |------|---------------|--------|-----------|
> | **A. 서버 API 키 업로드** | Shuffla GCP 프로젝트 | ❌ 10,000 units/일 = 6영상/일 | 낮음 |
> | **B. 사용자 OAuth 업로드** | 사용자별 Google 계정 | ✅ 사용자마다 독립 할당량 | 중간 |
> | **C. 하이브리드** | 기본은 B, 폴백 시 A | ✅ 최적 | 높음 |
>
> **권장: 방식 B (사용자 OAuth 기반)**
> - 각 사용자가 본인 YouTube 채널에 OAuth 2.0으로 연결
> - 업로드 시 사용자의 access token 사용 → Shuffla 서버 할당량 소진 없음
> - 사용자 1명당 하루 6개 업로드 → 30일 프로젝트를 5일에 걸쳐 자동 업로드
> - 또는 사용자가 본인 GCP 프로젝트 할당량 연장 신청 가능
>
> **할당량 최적화 기법:**
> 1. **`part` / `fields` 파라미터 활용** — 부분 리소스 조회로 불필요한 데이터 전송 최소화
> 2. **ETag 캐싱** — `If-None-Match` 헤더로 변경된 리소스만 재조회 (304 Not Modified 시 0 units)
> 3. **gzip 압축** — `Accept-Encoding: gzip` + User-Agent에 "gzip" 포함으로 대역폭 절감
> 4. **업로드 예약 분산** — 30영상을 한 번에 업로드하지 않고 일 1~2개씩 분산 예약
> 5. **할당량 연장 신청** — [Quota Extension Request Form](https://support.google.com/youtube/contact/yt_api_form)으로 추가 할당량 요청

- **현재:** 나레이션 음성만 존재 (BGM 없음)

  - 장르/무드 기반 자동 선택 (LLM이 씬 분위기 태깅)
  - 음량 자동 믹싱 (나레이션 -3dB, BGM -20dB)
- **가치:** 영상 퀄리티 대폭 향상, 유튜브 알고리즘 선호

#### ④ 자동 재생성 / A/B 테스트
- **현재:** 1일 1영상, 재생성 시 24시간 대기
- **확장:** 
  - 동일 제목으로 2~3개 변형 영상 생성 (다른 스톡 영상, 다른 나레이션 톤)
  - 업로드 후 조회수 비교 → 다음 영상에 피드백
- **가치:** 데이터 기반 콘텐츠 최적화
- **난이도:** 중 (조회수 API 연동 + 피드백 루프 필요)

- **확장:** 
  - TikTok, Instagram Reels, 네이버 TV 동시 크로스포스팅
  - 플랫폼별 최적화 (해시태그, 비율, 길이 제한)
  - 채널별 독립 진행 상태 관리
- **가치:** 1영상 제작으로 4플랫폼 동시 배포 → ROI 4배
- **난이도:** 상 (플랫폼별 API 정책 상이, TikTok은 자동 업로드 제한적)

#### ⑥ 트렌드 기반 주제 자동 발굴
- **현재:** 사용자가 주제 수동 입력
- **확장:** 
  - YouTube Trends API, Google Trends, 네이버 데이터랩 연동
  - 주기적 트렌드 크롤링 (Inngest 백그라운드 잡 이미 존재)
  - "이번 주 뜨는 주제 5개" 추천 → 원클릭 프로젝트 생성
- **가치:** 주제 선정 실패 확률 감소, 초기 채널 성장 가속
- **난이도:** 중 (트렌드 데이터 수집 + 랭킹 알고리즘)

#### ⑦ 썸네일 A/B 최적화
- **현재:** 영상 1초 지점 정지 화면 자동 추출
- **확장:** 
  - LLM으로 클릭 유도 썸네일 텍스트 생성
  - DALL-E / gpt-image-1로 커스텀 썸네일 생성
  - 3종 변형 생성 → 업로드 후 클릭률 비교
- **가치:** CTR(클릭률) 20~50% 향상 가능
- **난이도:** 중 (이미지 생성 API 연동, 텍스트 오버레이 렌더링)

### 5.3 장기 확장 (12개월+)

#### ⑧ AI 영상 생성 도입 (옵션)
- **현재:** 스톡 영상 잘라 붙이기 (원가 $0.06/영상)
- **확장:** 
  - Seedance / Kling / Sora 연동으로 씬별 맞춤 영상 생성
  - "스톡 모드" vs "AI 생성 모드" 토글 (프라이싱 차등)
  - 하이브리드: 스톡 영상 + AI 생성 영상 혼합
- **가치:** 독창적 영상, 스톡에 없는 주제 대응
- **원가:** 영상당 $0.30~$2.00 추가 → 프리미엄 플랜 필요
- **난이도:** 중 (이미 ByteDance Seedance provider 존재)

#### ⑨ 채널 분석 대시보드
- **확장:** 
  - YouTube Analytics API 연동 (조회수, 시청 지속 시간, 구독자 증가)
  - 어떤 주제/제목이 성과가 좋은지 자동 분석
  - 다음 30일 플래너에 성과 피드백 반영
- **가치:** 데이터 기반 채널 성장, 장기 리텐션
- **난이도:** 상 (분석 모델 + 피드백 루프 설계)

#### ⑩ 화이트라벨 / B2B SaaS
- **확장:** 
  - 에이전시/기업용 화이트라벨 솔루션
  - 다수 클라이언트 채널 관리 (멀티 테넌트)
  - 커스텀 브랜딩, 팀 협업, 승인 워크플로우
- **가치:** ARPU 10배 이상 상승 (B2B 프라이싱)
- **난이도:** 상 (멀티 테넌트 아키텍처, 권한 체계 재설계)

## 6. 문제점 및 리스크 분석

### 6.1 기술적 문제

#### 🔴 P0: 렌더링 타임아웃 리스크
- **문제:** Vercel 서버리스 `maxDuration = 600s` (10분). 30일 영상을 한 번에 렌더링하면 타임아웃 가능
- **현재 상태:** 영상 1개씩 개별 렌더링하므로 1개당 ~30초로 문제 없음
- **잠재 리스크:** 씬 수 증가, 고해상도 렌더링, BGM 추가 시 렌더링 시간 증가
- **해결方案:** 
  - Inngest 백그라운드 잡으로 렌더링 비동기화 (이미 Inngest 인프라 존재)
  - 렌더링 큐 + 진행률 폴링 구조
  - 영상 길이/씬 수에 따른 동적 타임아웃

#### 🔴 P0: 스톡 영상 품질/가용성 불안정
- **문제:** Pexels/Pixabay에 적절한 영상이 없으면 `mock` 후보가 들어가 렌더링 실패
- **현재 상태:** `videoUrl: null`인 mock 후보는 렌더링 단계에서 에러 발생
- **해결方案:**
  - 영상이 없을 때 LLM이 검색 키워드를 자동 확장/재시도
  - 폴백 영상 풀(범용 배경 영상) 사전 확보
  - AI 영상 생성을 최후의 폴백으로 (Seedance)

#### 🟡 P1: TTS 음성 다양성 부족
- **문제:** OpenAI TTS 6종(영어 원어민 톤)만 지원. 한국어 특화 음성 없음
- **영향:** 한국어 나레이션이 자연스럽지 않을 수 있음 (양양/억양)
- **해결方案:**
  - ElevenLabs 연동 (한국어 다국어 음성, 커스텀 보이스)
  - 네이버 CLOVA Dubbing API (한국어 특화)
  - Google Cloud TTS (Wavenet 한국어 음성)

#### 🟡 P1: 자막 스타일 고정
- **문제:** ASS 자막이 Pretendard 폰트, 단일 스타일로 고정
- **해결方案:** 
  - 자막 스타일 프리셋 (5~10종: 미니멀, 시네마틱, 유튜브 스타일 등)
  - 채널별 자막 스타일 메모리 (Brand editorPreferences 재사용 패턴 적용)

#### 🟢 P2: 영상 품질 균일성
- **문제:** 스톡 영상마다 해상도/비율/품질이 달라 최종 영상 품질이 불균일
- **현재 대응:** `normalizeClip()`에서 1080x1920 강제 리사이즈 + 크롭
- **개선:** 품질 점수 기반 스톡 영상 랭킹 (해상도, 비트레이트, 화면 안정성)

### 6.2 비즈니스적 문제

#### 🔴 P0: YouTube 자동 업로드 미지원
- **문제:** 현재 MP4 다운로드 후 수동 업로드. "자동화"라는 이름에 비해 마지막 단계가 수동
- **영향:** 사용자가 매일 업로드를 까먹으면 채널 성장이 멈춤. 리텐션 저하
- **해결方案:** YouTube Data API v3 연동 (OAuth 2.0, 예약 업로드)
- **우선순위:** 최우선. 없으면 서비스 가치가 반감됨
- **할당량 제약:** 영상 업로드 1회당 1,600 units. 기본 10,000 units/일 = 하루 6개. **반드시 사용자 OAuth 기반 업로드로 설계**하여 서버 할당량 소진을 방지해야 함. 자세한 내용은 §5.1 ① 참조

#### 🟡 P1: 플랜 간 YouTube 자동화 차별성 부재
- **문제:** Creator(25,000원)와 Studio(39,000원)가 동일한 30영상 제공
- **영향:** Studio 업그레이드 동기 부족. ARPU 상승 한계
- **해결方案:** 
  - Studio: 60영상(2프로젝트) 또는 멀티 채널 지원
  - 크레딧 기반으로 전환하여 사용량에 비례한 과금

#### 🟡 P1: 콘텐츠 중복/표절 리스크
- **문제:** 동일 주제로 여러 사용자가 비슷한 영상을 양산할 수 있음
- **영향:** YouTube 중복 콘텐츠 정책 경고, 채널 정지 리스크
- **해결方案:**
  - LLM 프롬프트에 변형 강제 (관점, 사례, 순서 랜덤화)
  - 스톡 영상 조합의 다양성 보장 (같은 키워드라도 다른 영상 선택)
  - 유사도 검사 (생성 후 자체 비교)

#### 🟢 P2: 무료 체험 부재
- **문제:** FREE 플랜은 YouTube 자동화 사용 불가. 체험 없이 결제 유도
- **영향:** 전환율 저하. "돈 내기 전에 품질을 모름"
- **해결方案:** 
  - 1회 무료 체험 (1영상만 렌더링 가능, 워터마크 포함)
  - 7일 무료 체험 (Creator 기능 전체, 자동 결제 전환)

### 6.3 운영적 문제

#### 🟡 P1: API 의존성 집중 리스크
- **문제:** OpenAI (LLM + TTS) 단일 의존. 장애 시 서비스 전면 중단
- **해결方案:**
  - LLM: Groq (이미 연동됨), Gemini (이미 연동됨) 폴백 체인 구축
  - TTS: ElevenLabs, Google Cloud TTS 폴백 준비
  - 헬스체크 + 자동 폴백 라우팅

#### 🟡 P1: 스토리지 비용 선형 증가
- **문제:** 영상 1개당 ~5MB. 사용자 1,000명 × 30영상 = 150GB/월
- **해결方案:**
  - 업로드 완료 후 일정 기간(7일) 후 자동 삭제 (이미 history-retention 패턴 존재)
  - 사용자가 다운로드하면 서버에서 즉시 삭제 옵션
  - Cold storage 아카이빙

#### 🟢 P2: 모니터링/관측성 부족
- **문제:** 렌더링 실패 시 원인 파악이 어려움 (ffmpeg stderr만 로깅)
- **해결方案:**
  - 구조화된 렌더링 로그 (씬별 성공/실패, 소요 시간, 원가)
  - 대시보드 (일일 렌더링 수, 실패율, 평균 소요 시간)
  - 에러 자동 수집 (errorLogger 이미 존재하므로 확장)

## 10. 결론

Shuffla YouTube 자동화는 **"한국어 쇼츠 30일 자동 생성"**이라는 명확한 가치 제안으로 원가 우위(영상당 ~80원)와 턴키 UX를 갖추고 있다. 핵심 성공 조건은 다음 세 가지다:

1. **자동 업로드 완성** — "다운로드 후 수동 업로드"를 없애야 진정한 자동화가 된다. YouTube Data API v3 연동이 최우선 과제다. **단, 영상 업로드 1회당 1,600 units의 할당량이 소진되므로, 반드시 사용자 OAuth 기반 업로드로 설계하여 서버 할당량(기본 10,000 units/일 = 6업로드)을 소진하지 않아야 한다.** 30영상을 일 1~2개씩 분산 예약 업로드하고, `part`/`fields` 파라미터와 ETag 캐싱으로 할당량을 최적화해야 한다.

2. **한국어 음성 품질** — OpenAI TTS 6종은 영어 원어민 톤으로, 한국어 채널에 자연스럽지 않을 수 있다. ElevenLabs 또는 CLOVA Dubbing 연동으로 한국어 특화 음성을 제공해야 한다.

3. **사용량 기반 프라이싱** — 현재 Creator/Studio 간 YouTube 자동화 차별성이 없다. 영상 수 또는 멀티 채널 기반으로 플랜을 차등화하여 ARPU를 끌어올려야 한다.

이 세 가지가 해결되면 Shuffla는 한국어 쇼츠 자동화 시장에서 명확한 1위 사업자로 자리매김할 수 있다.
